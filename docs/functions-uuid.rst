UUID Functions
==============

.. contents::
   :local:
   :depth: 1

UUID functions generate a universally unique identifier (UUID, see RFC 9562),
and convert one between its text and a ``BINARY(16)``. The text is 32 lower
case hexadecimal digits in groups of 8, 4, 4, 4 and 12, separated by dashes,
such as ``f81d4fae-7dec-11d0-a765-00a0c91e6bf6``.

.. note::

   The random bits of a UUID come from the operating system's
   cryptographically secure random number generator (not the one that
   ``RANDOM`` uses), so a UUID can't be predicted from the ones before it. A
   version 4 UUID has 122 random bits, so it can be used where it must not be
   guessed, such as a token in a link. A version 7 UUID has 62 random bits,
   which is still too many to guess, but anyone who sees it can tell when it
   was generated, to within a fraction of a millisecond.

A UUID can be stored as text (``CHARACTER(36)``), or in less than half of the
space as a ``BINARY(16)`` with ``UUID_TO_BINARY`` and ``BINARY_TO_UUID``.

The generators return a different value each time, so they can't be in a
``CHECK`` constraint.

BINARY_TO_UUID
^^^^^^^^^^^^^^

.. code-block:: sql

   BINARY_TO_UUID(BINARY VARYING) CHARACTER VARYING(36)

Converts the 16 octets of a UUID to its text, in lower case. A binary string
that isn't 16 octets is a ``22018`` error. It's the opposite of
``UUID_TO_BINARY``.

``BINARY_TO_UUID`` is a vsql extension flagged by ``V407-04`` (see
:doc:`sql-flagging`).

**Examples**

.. code-block:: sql

  VALUES BINARY_TO_UUID(X'F81D4FAE7DEC11D0A76500A0C91E6BF6');
  -- COL1: f81d4fae-7dec-11d0-a765-00a0c91e6bf6

**Compatibility**

- **SQL standard:** not standard.
- **Other databases:**

  - MySQL: ``BIN_TO_UUID``.
  - PostgreSQL: ``ENCODE(value, 'hex')::UUID::TEXT``.
  - SQL Server: ``CAST(value AS UNIQUEIDENTIFIER)``, which has the first three
    groups in the opposite byte order.
  - Oracle: ``LOWER(REGEXP_REPLACE(RAWTOHEX(value),
    '(.{8})(.{4})(.{4})(.{4})(.{12})', '\1-\2-\3-\4-\5'))``.
  - SQLite: none built in.

GENERATE_UUID_V4
^^^^^^^^^^^^^^^^

.. code-block:: sql

   GENERATE_UUID_V4() CHARACTER VARYING(36)

A version 4 UUID, which is random (other than the 6 bits of its version and
variant). It's the most common kind of UUID.

``GENERATE_UUID_V4`` is a vsql extension flagged by ``V407-01`` (see
:doc:`sql-flagging`).

**Examples**

.. code-block:: sql

  VALUES GENERATE_UUID_V4();
  -- COL1: 0b5d2e8f-31c4-4a6e-9f02-7c1d8e3b5a64

**Compatibility**

- **SQL standard:** not standard.
- **Other databases:**

  - PostgreSQL: ``GEN_RANDOM_UUID`` or ``UUIDV4`` (18 and later).
  - MySQL: ``UUID`` is version 1 (based on the time and the host), not random.
  - SQL Server: ``NEWID``, in upper case.
  - Oracle: ``SYS_GUID`` is 16 random octets, not a version 4 UUID.
  - SQLite: none built in.

GENERATE_UUID_V7
^^^^^^^^^^^^^^^^

.. code-block:: sql

   GENERATE_UUID_V7() CHARACTER VARYING(36)

A version 7 UUID, which starts with the time (in milliseconds since
1970-01-01 00:00:00 UTC, and then a fraction of the millisecond), and the rest
is random. They sort in the order they were generated, so they make a better
primary key than a version 4 UUID: new rows go at the end of the index, rather
than anywhere in it.

Each UUID that a connection generates is greater than the last one, even when
two are generated in the same fraction of a millisecond or the clock goes
backwards. UUIDs generated by different connections at about the same time
may not be in order.

``GENERATE_UUID_V7`` is a vsql extension flagged by ``V407-02`` (see
:doc:`sql-flagging`).

**Examples**

.. code-block:: sql

  VALUES GENERATE_UUID_V7();
  -- COL1: 019a8c6e-4b21-7d3a-8e5f-2a9c4b7d1e03

  VALUES GENERATE_UUID_V7() < GENERATE_UUID_V7();
  -- COL1: TRUE

**Compatibility**

- **SQL standard:** not standard.
- **Other databases:**

  - PostgreSQL: ``UUIDV7`` (18 and later).
  - MySQL, SQLite, SQL Server and Oracle: none built in.

UUID_TO_BINARY
^^^^^^^^^^^^^^

.. code-block:: sql

   UUID_TO_BINARY(CHARACTER VARYING) BINARY(16)

Converts the text of a UUID (with digits in upper or lower case) to its 16
octets. Anything that isn't 8, 4, 4, 4 and 12 hexadecimal digits separated by
dashes, including without the dashes or in braces, is a ``22018`` error.

``UUID_TO_BINARY`` is a vsql extension flagged by ``V407-03`` (see
:doc:`sql-flagging`).

**Examples**

.. code-block:: sql

  VALUES UUID_TO_BINARY('f81d4fae-7dec-11d0-a765-00a0c91e6bf6');
  -- COL1: F81D4FAE7DEC11D0A76500A0C91E6BF6

  CREATE TABLE users (id BINARY(16) PRIMARY KEY, name VARCHAR(50));
  INSERT INTO users VALUES (UUID_TO_BINARY(GENERATE_UUID_V7()), 'Alice');

**Compatibility**

- **SQL standard:** not standard.
- **Other databases:**

  - MySQL: ``UUID_TO_BIN``, which also accepts the UUID without dashes or in
    braces.
  - PostgreSQL: ``DECODE(REPLACE(text, '-', ''), 'hex')``.
  - SQL Server: ``CAST(CAST(text AS UNIQUEIDENTIFIER) AS BINARY(16))``, which
    has the first three groups in the opposite byte order.
  - Oracle: ``HEXTORAW(REPLACE(text, '-', ''))``.
  - SQLite: ``UNHEX(REPLACE(text, '-', ''))``.
