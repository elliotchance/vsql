INSERT
======

.. contents::

Syntax
------

.. code-block:: text

  INSERT INTO <table_name> [ ( <column_name> , ... ) ]
  [ OVERRIDING { SYSTEM | USER } VALUE ]
  { VALUES ( <value> , ... ) , ... | <query> }
  [ ON CONFLICT [ <conflict_target> ] DO NOTHING
  | ON CONFLICT <conflict_target> DO UPDATE SET <column_name> = <value> , ...
    [ WHERE <condition> ] ]
  [ RETURNING { * | <expression> [ AS <name> ] } , ... ]

  <conflict_target> ::=
      ( <column_name> , ... )
    | ON CONSTRAINT <constraint_name>

  INSERT INTO <table_name> DEFAULT VALUES

Without a list of columns, it's every column in the order of the table.

``DEFAULT VALUES`` inserts one row where every column gets its default, the
same as ``VALUES (DEFAULT, ...)`` with a ``DEFAULT`` for each column. Identity
columns get their next value, generated columns are set from the defaults of
the other columns, and a column without a default is ``NULL`` (an error
``23502`` for a ``NOT NULL`` column).

The rows are either the rows of ``VALUES``, or the result of a query (see
:doc:`select`). A query can use ``UNION``, ``EXCEPT``, ``INTERSECT``,
``ORDER BY``, ``OFFSET`` and ``FETCH FIRST``, and it can be in parentheses. Its
result is known before any row is inserted, so a query that reads from the same
table doesn't see the new rows. A ``VALUES`` on its own is always the first form, ``(VALUES ...)`` or
``VALUES ... UNION ...`` is a query, which can't contain ``DEFAULT`` or a
``NULL`` on its own.

Each row must have the same number of values as there are columns, which is an
error ``42601`` otherwise. Columns that aren't listed get their default (see
:doc:`create-table`), which is ``NULL`` if the column doesn't have one. ``NULL``
is an error ``23502`` for a ``NOT NULL`` column, and a row that violates a
``CHECK`` constraint is an error ``23514``. If any row fails, none of the rows
are inserted.

A value in ``VALUES`` can be ``DEFAULT``, which is the default value of the
column.

The value of a generated column must be ``DEFAULT`` in ``VALUES`` (an error
``428C9`` otherwise). A query can have any value of a suitable type for a
generated column, but it's ignored, so ``INSERT INTO t SELECT * FROM t`` works.

An identity column (see :doc:`create-table`) gets the next value of its
sequence when it isn't listed, or its value is ``DEFAULT``. Any other value for
a ``GENERATED ALWAYS`` identity column is an error ``428C9``, unless the
``INSERT`` has ``OVERRIDING SYSTEM VALUE``. A query for that column always needs
one of the ``OVERRIDING`` clauses, even if it has no rows.
``OVERRIDING USER VALUE`` ignores
the values for the identity column, so it always gets the next value. Values
that are inserted don't change the sequence. ``OVERRIDING SYSTEM VALUE`` can't
be used for a ``GENERATED BY DEFAULT`` identity column, and neither can be used
without the identity column (both are an error ``42601``).

The values are converted to the types of the columns. For example, a number
that's too large for the column is an error ``22003``, and a string that's too
long is an error ``22001``.

The result (such as ``INSERT 2``) contains the number of rows inserted. A query
without any rows is ``INSERT 0`` with a warning ``02000`` (no data).

RETURNING
---------

With ``RETURNING``, the result is a row for each row that's inserted (including
the values of defaults and identity columns), like a query, rather than the
number of rows. The list is the same as the list of a ``SELECT``, and a column
can be qualified with the name of the table:

.. code-block:: sql

  CREATE TABLE products (id INT GENERATED ALWAYS AS IDENTITY, title VARCHAR(50));
  INSERT INTO products (title) VALUES ('Kettle'), ('Toaster') RETURNING id, products.title;
  -- msg: CREATE TABLE 1
  -- ID: 1 TITLE: Kettle
  -- ID: 2 TITLE: Toaster

It's the same as ``SELECT ... FROM NEW TABLE (INSERT ...)`` (see
:doc:`select`). ``UPDATE`` and ``DELETE`` can also have a ``RETURNING`` (see
:doc:`update` and :doc:`delete`). ``RETURNING`` isn't standard SQL, so it's
flagged as ``V119-01`` (see :doc:`sql-flagging`).

ON CONFLICT
-----------

``ON CONFLICT`` (an "upsert") handles a new row that has the same values as an
existing row in a ``PRIMARY KEY``, ``UNIQUE`` constraint or ``UNIQUE`` index,
rather than failing with an error ``23505``. It works like PostgreSQL and
SQLite:

- ``DO NOTHING`` skips the new row.
- ``DO UPDATE SET ...`` updates the existing row instead, like an
  :doc:`update`. ``EXCLUDED`` is the row that would have been inserted
  (including its defaults), and the name of the table is the existing row. A
  column must be qualified with one of them, since it's in both. A ``WHERE``
  only updates the rows where it's true, and skips the others.

.. code-block:: sql

  CREATE TABLE pages (slug VARCHAR(20) NOT NULL PRIMARY KEY, title VARCHAR(50), views INT DEFAULT 0);
  INSERT INTO pages (slug, title) VALUES ('home', 'Home');
  INSERT INTO pages (slug, title) VALUES ('home', 'Welcome'), ('about', 'About')
    ON CONFLICT (slug) DO UPDATE SET title = EXCLUDED.title, views = pages.views + 1;
  SELECT * FROM pages;
  -- msg: CREATE TABLE 1
  -- msg: INSERT 1
  -- msg: INSERT 2
  -- SLUG: about TITLE: About VIEWS: 0
  -- SLUG: home TITLE: Welcome VIEWS: 1

The conflict target chooses which constraints are checked: a list of columns
matches each ``PRIMARY KEY``, ``UNIQUE`` constraint or ``UNIQUE`` index with
exactly those columns (in any order), and ``ON CONSTRAINT`` names a
``PRIMARY KEY`` or ``UNIQUE`` constraint. A conflict in any other constraint is
still an error ``23505``. ``DO NOTHING`` can leave out the conflict target to
skip a row that conflicts in any of them, but ``DO UPDATE`` needs one. It's an
error ``42601`` if nothing matches the columns, or if one of the constraints is
``DEFERRABLE``, and an error ``42704`` if the named constraint doesn't exist.

Each row is checked in order, so a row also conflicts with a row that the same
``INSERT`` inserted (``DO NOTHING`` keeps the first one). ``DO UPDATE`` can't
change the same row more than once, since the result would depend on the order
of the rows, which is an error ``21000``. A row with a ``NULL`` in one of the
columns never conflicts, unless the constraint is ``NULLS NOT DISTINCT``. Like
a ``PRIMARY KEY`` or ``UNIQUE`` constraint, a row that another transaction has
inserted or deleted, and not yet committed, is an error ``40001`` (serialization
failure) instead of waiting for it.

The count (such as ``INSERT 2``) and the rows of ``RETURNING`` (or
``NEW TABLE``) are the rows that were inserted or updated, including a row that
was updated to the same values, but not the rows that were skipped.

``ON CONFLICT`` isn't standard SQL, so it's flagged as ``V119-02`` (see
:doc:`sql-flagging`). The standard way to do the same thing is :doc:`merge`.
``CONFLICT``, ``DO``, ``NOTHING`` and ``EXCLUDED`` aren't key words, so they can
still be used as names.

Examples
--------

.. code-block:: sql

  CREATE TABLE products (title VARCHAR(50), price NUMERIC(10, 2));
  INSERT INTO products (title, price) VALUES ('Instant Pot', 144.89);
  INSERT INTO products (title, price) VALUES ('Kettle', 30), ('Toaster', 25.5);
  INSERT INTO products VALUES ('Blender', 60);
  INSERT INTO products (title, price)
    SELECT title, price * 2 FROM products WHERE price < 30;
  SELECT * FROM products;
  -- msg: CREATE TABLE 1
  -- msg: INSERT 1
  -- msg: INSERT 2
  -- msg: INSERT 1
  -- msg: INSERT 1
  -- TITLE: Instant Pot PRICE: 144.89
  -- TITLE: Kettle PRICE: 30.00
  -- TITLE: Toaster PRICE: 25.50
  -- TITLE: Blender PRICE: 60.00
  -- TITLE: Toaster PRICE: 51.00
